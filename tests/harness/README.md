# Managed native tests

The adapter supports Node 24 and later. Declare a run with the shared `RunOptions` from `resources/run.js`:

```js
import { test, subtest, after } from './node.js';

test('directory consumer', options, async function (context, scope) {
    const owned = await scope.directory('case');
    after(context, async function (actual) {
        // A fallible case hook receives the real native context as argument and receiver.
    });
    await subtest(context, 'child', async function (child) {
        // Use owned.path while this managed run remains active.
    });
});
```

`test(name, options, body)` admits its run during execution. Its body receives the real native context, resource scope and TestRun. A real native parent owns that callback as a child. Its own `after` hook and terminal signal enter the same idempotent resource cleanup, covering cancellation and earlier hooks that prevent dispatch of that `after`. Cleanup closes admission, joins admitted work and disposes resources. Normal terminal dispatch follows all owner hooks; publication resumes after its synchronous native child aggregation and resource closure. Early cancellation records its sticky failure before signaling. Neither a cleanup turn nor a signal alone proves a passed outcome. The known owner's completed outcome determines the run status. Native output contains the root owner and body registrations. Consumers supply no final cleanup callback.

The returned promise fulfills with the completed RunSummary for an admitted run, including a failed test outcome. Admission, cleanup or persistence faults reject it and fail the native command through the adapter's final hook. Rejected admission retains its original persistence error alongside a concurrent native cancellation. No RunSummary is invented for a rejected admission. Recorded managed errors still reject completion and fail the command when native `todo` or expected-failure handling would otherwise permit success.

The root return is a result-observation promise, not a selection-independent native ancestor join. An owning callback omitted by native selection or an inherited hook resolves with `undefined` at the module's final hook and allocates no run. Observe it nonblockingly from an executing ancestor: awaiting that ancestor's own module-finalization result forms a cycle. Inside an executing managed case, use `subtest` for native child registration. Entered roots can settle before module end. An omitted owner's native failure, when present, remains in native diagnostics; `undefined` is not a passed RunSummary. Owning and module final hooks close registration before awaiting work. A cancelled or terminal callback entrance cannot subsequently admit a run. Module import also allocates nothing.

`subtest(context, name, optionsOrCallback, callback?)` immediately registers a single native `context.test` with the supplied options. It returns that exact native value unchanged: Node 24.0.0 returns `undefined`; runtimes returning a completion promise retain that promise and its fulfilled-undefined semantics. Native scheduling, rather than awaiting an invented promise, determines execution. Managed children have no additional owner/body name segment or hook entrance.

Native validation, option consumption, scheduling, filtering, skip, signals, assertion plans and deadlines apply to that registration. Later mutation of a queued registration's options does not create another native options read. The adapter associates a child only through its own callback, never through inherited hook arrivals. Entered children retain their actual completed Error. Callback-less failures retain the true owning outcome and original native diagnostics; an unused signal is not attached to an aggregate child failure. Callbacks must finish their asynchronous work, including responding to cancellation.

`after(context, callback)` delegates to the actual `context.after`. Managed subtest and hook callbacks receive the native argument and receiver. The supported callbacks are synchronous or Promise-based: body arguments are context/scope/run, subtest and hook arguments are context. Error-first callback signatures and hook options are outside this API.

Managed hooks use the same terminal callback-entrance boundary. A hook already executing is joined before finalization; a native hook arriving after its registration has completed cannot start managed work.

Use managed subtest/hook registration for complete callback-origin capture. Raw `context.test` and `context.after` still affect the genuine native outcome. Their completed parent Error is retained; original raw errors available from native output remain diagnostic evidence. A distinct raw hook Error discarded by native execution after a body failure cannot be reconstructed. The adapter requires no reporter or worker channel; the structured reporter under `fixtures/` records test evidence only.

`TestRun.dispose()` closes resource admission and releases resources without publishing an outcome. It returns the same disposal receipt on repeated calls and rejects with the original cleanup aggregate. `finish(outcome)` delegates to that same disposal and publishes the final summary, retaining cleanup errors. The native adapter owns both phases.

## Declared seed and profile inputs

`materializeSeed(scope, { fixture, configOverrides, settingsOverrides })` returns `dataRoot`, `configPath`, `manifestPath` and the original `owner` and `dataOwner` directory receipts. An omitted fixture selects tracked config and default settings. An explicit defaults fixture can select `defaultsRoot` and `{ source, path }` files; compatibility requires `{ kind: 'compatibility', root }`. Sources remain read-only, complete selected bytes and empty directories are copied, and compatibility input is not filtered. `{ kind: 'owned', directory }` preserves verified registered data in place and creates a separate configuration container; settings overrides apply to generated or copied input. Config/settings overrides merge mappings and replace scalar/array values. The source/output manifest records paths, byte lengths and hashes. Original directory identities are revalidated after acquisition. The framework owns target release.

`getProfile(name, { files }?)` reads declared coverage without loading runners or allocating execution resources. Stable names are unit, storage-local, storage-sql, e2e, frontend, skills-ui, desktop, desktop-packaged and compatibility. Exact file filters keep the same diagnostic slot and refuse unknown or empty selections. Local storage selects filesystem/SQLite; SQL requires both external database protocols. Compatibility declares mandatory explicit input. Missing browser-runner coverage remains explicit rather than treating pure module tests as browser execution.

`coverage-map.json` retains symbolic behavior declarations, selected backend/matrix contracts, resources, fixtures and profile membership. `validateCoverageMap(files, mapping)` compares paths or observed contracts and reports omissions, duplicates and lost backend/behavior/resource/matrix coverage. Catalog entries declare migration targets, not executed-case counts. Existing runner/server/database call sites are adopted by the later framework tasks; writing seed files alone does not initialize a database or replace those adapters.

## Managed storage leases

Jest runs the storage suites as the `storage-local` and `storage-sql` projects declared in `jest.config.json`. The local project disables external backends before test modules load. The SQL project authenticates both servers in setup and fails when either dependency is unavailable.

`testWithResources` and `suiteResources` declare the managed case or suite scope. The storage hooks install a case scope before each test. Allocating harnesses accept an optional explicit `{ scope }`; omission reads that active case scope and fails when none is active. This applies to the filesystem, SQLite, MySQL and PostgreSQL contract harnesses and to `makeEndpointHarness`.

`acquireMysqlDatabase` and `acquirePostgresDatabase` register namespaces before creation and write secret-free `lease.json` receipts with the full resource identity, authenticated server identity and remote ownership proof. Namespace URLs remain runtime values. Fresh namespaces contain no migrated tables. PostgreSQL schemas and non-reused MySQL namespaces are dropped on release after ownership verification.

`acquireMysqlDatabase(scope, rootUrl, { reuse: true })` gives the nearest worker or run scope ownership of the physical namespace. Case leases depend on that resource. Release empties and fingerprints the namespace; subsequent cases reuse only a matching schema. Drifted namespaces are retired, and normal worker or run completion releases the physical database. The MySQL engine harness requests reuse for non-fresh leases.

## Managed browser execution

Use `defineManagedConfig(config, import.meta.filename)` from `playwright-config.js` with the managed setup, teardown and reporter modules. Set `preserveOutput: 'always'`; native contexts and tracing remain framework-owned. Read-only configuration validation checks project output, managed reports and built-in reporter destinations, including their environment and command-line selection, before native output cleanup. Overlap with the resource registry is rejected. Formatter declarations or `--reporter` overrides include the managed reporter beside the chosen format reporters. Configuration loading and `--list` do not allocate execution resources.

Import `test` and `expect` from `playwright.js`. Automatic fixtures expose `resources` for an isolated case and `workerResources` for the current native worker. Declare shared file state with `await workerResources.scenario(testInfo.file)`. Capabilities expose `child`, `directory`, `verifyDirectory`, `borrowDirectory`, `process` and `captureDiagnostic`; directory handles and process dependencies refer to their original registered identities. Ordinary fixture files inherit their owned directory. Explicit process `stop` supports behavior such as restart, while final release belongs to the framework.

Actual scopes and application owners remain in the runner. Worker teardown closes admission and cancels unfinished startup; native `testEnd` supplies complete attachments before the runner releases case or scenario data. Capture errors retain other readable attachments and fail the command. Awaited final reporting joins all admitted work after native global teardown, retains original native results and publishes the actual resource outcome. A successful native retry keeps its failed-attempt errors and readable failure artifacts without becoming an additional infrastructure failure; resource, capture and cleanup errors still fail final reporting. An unexecuted project does not acquire an empty failure slot because another project failed.

The native lifecycle suite exercises a real browser, HTTP fixture processes, product startup, disk state and original tracing. A retained failure trace is readable only after its complete archive, every entry and its checksum pass verification, including large source artifacts. Existing caller adoption and complete product regression remain subsequent acceptance gates.

## Owned application startup

`startServer({ scope, batchKey, scenarioId, extraEnv, extraConfig, data })` from `server.js` starts the real application with a registered process and declared inputs. Local and browser-worker scopes provide the same `process` and `verifyDirectory` capabilities. Default startup uses tracked seed data, filesystem storage and an OS-assigned loopback port. `extraConfig` contains nested mappings; `extraEnv` is forwarded explicitly. Existing owned data retains its original verified path; explicitly borrowed data is copied into owned storage.

The handle exposes `baseURL`, `port`, `pid`, `resourceId`, `dataRoot`, `configPath`, `manifestPath`, `owner` and `dataOwner`. `stop()` joins process termination while retaining data; `restart()` reuses the data and bound URL. Configuration and data paths are checked inside their registered containers before launch. Occupied ports and invalid startup retain their actual errors and registered cleanup responsibility. The framework supplies final process and data release.

## Owned processes

```js
import { launchOwnedProcess } from './resources/process-owner.js';

test('scenario restart', options, async (context, scope) => {
    const data = await scope.directory('scenario');
    const launch = () => launchOwnedProcess(scope, {
        label: 'scenario service',
        command: [process.execPath, serviceFixture, data.path],
        readyLine: 'service-ready',
        dependsOn: [data.resourceId],
    });
    const first = await launch();
    await first.stop();
    const second = await launch();
    // The same admitted data remains available until scope disposal.
});
```

`launchOwnedProcess(scope, options)` and `scope.process(options)` register responsibility before creating a controller or worker. The actual controller is published before worker launch; the worker's native identity is published before readiness returns a ProcessLease. A string `readyLine` matches an exact stdout line. `{ pattern }` matches a complete line with a validated Unicode expression after removing terminal formatting; `lease.readyLine` retains the original complete decoded line. `command`, optional `cwd` and optional `env` configure the real child. Mutable data must be an explicit resource dependency. `stop()` returns the same promise on repeated calls, waits for actual worker/controller exit and leaves scenario data intact. `exited` observes the actual worker exit after registry publication. Unexpected worker exit records a run failure. Final disposal stops dependent processes before deleting their directories; unresolved process disposal retains dependent data.

Process input containers are captured at the public call. Later caller changes do not alter the validated command, environment, declared values or dependencies; the supplied cancellation signal remains live. NUL in executable, arguments, cwd or environment is rejected before process admission. Readiness decodes streaming UTF-8 and matches complete stdout lines, including CRLF.

The termination policy defaults to `SIGTERM`. Select `stopSignal: 'SIGKILL'` explicitly for a child that does not cooperate with `SIGTERM`. The framework does not add a timed escalation or substitute a different policy after failure.

The native adapter supplies its actual owner cancellation signal to admitted process startup. An explicit `signal` can select a narrower cancellation boundary. Cancellation retains its original reason through the shared error boundary; Error reasons retain identity. No handle is invented. Startup failure retains its log and releases the actual partial child before rejection. Port conflicts have `EADDRINUSE`; a missing executable retains its native spawn diagnostic. Child stdout/stderr are diagnostic text, not native-test result transport.

Process arguments and environment are not persisted as resource configuration. Transported output, structured native failure graphs and startup logs redact supplied environment values and `sensitiveValues`, including values split across output fragments. Diagnostic transformation preserves useful native properties, causes and references without mutating original Errors. Supply `sensitiveValues` for credentials a child obtains outside the supplied environment. Run command evidence must not contain credentials. Startup logs remain beside the registry; diagnostic retention/export belongs to the diagnostic provider.

The shared failure graph stores caller properties as ordered `{ name, value }` entries. Redaction transforms payload names and values, including accessor names, resource data and publication data. Colliding displayed names retain their separate slots. Trusted IPC, terminal and registry receivers validate and freeze graphs; subsequent wrappers preserve their schema while importing identities and references into the enclosing graph. Caller objects resembling that schema remain ordinary redacted payload. Readers select distinct ordered entries instead of projecting redacted names into object keys.

Generated replacement text carries validated payload-slot ranges in the shared representation. Later diagnostic projection preserves those ranges instead of redacting its own marker; literal marker text remains payload. Captured declaration batches apply in admission order, with longest matches selected within a batch. Registry snapshots retain only lengths and SHA256 matching rules for replaying that projection during recovery. Raw declaration values are not persisted.

The persisted policy is explicitly tagged `literal-utf16le-sha256-v1`. Digests cover exact UTF-16LE code units, preserving literal matching for supplementary characters, replacement characters and isolated surrogates. Recovery validates actual JSON field types before writer custody or registry changes. Untagged policies cannot establish this encoding contract and are refused with the run identity and data retained. Unchanged prior failure graphs preserve their serialized field order.

## Failure diagnostics

`captureDiagnostic(scope, { name, bytes, contentType })` copies complete byte arrays at admission. `scope.diagnostic({ name, contentType, produce, stage })` registers a deferred producer in the `capture` or `complete` stage. Names are plain filenames; references record actual hash, length, content type, file identity and reading status. `readDiagnostic(index, ref)` and `exportDiagnostic(index, newAbsoluteDestination)` verify registered ownership and readable complete bytes. Repeated content shares a run-local object without truncation or lossy encoding.

Resource disposal closes admission and performs early capture. It initiates registered `drain` actions across the sealed scope subtree before joining admitted continuations, then joins both actions and operations before `complete` trace closure and dependent resource release. A continuation receives the run's actual cancellation signal. Register trace closure in `complete` before its deferred diagnostic producer. Capture and finalization errors remain in the same original-error store and do not prevent other cleanup attempts. Capture revalidates its registered directory chain after metadata awaits and before native file mutation.

The existing native adapter stages artifacts during resource-only disposal and publishes only after the actual known owner result. `publishFailure(run, outcome)` joins that run's idempotent finish. Immutable index versions and byte objects live separately from runtime data; an atomic stable profile slot selects the latest complete failure. Filters and worker arguments do not create slots. Passing reruns discard only their own staging. Exclusive profile publication custody orders concurrent publishers. Published predecessor links locate superseded bundles; only their own registry's durable retirement intent and completion authorize removal. Retirement holds that run's exclusive writer custody through its final save and skips a busy run without waiting under profile custody. Unknown files and missing bundles without that exact durable intent remain errors; completed retirement reconciles superseded registries without republishing older slot bytes. The `run-diagnostics-v2` representation refuses older retirement metadata rather than interpreting copied worklists as deletion authority.

Prepare faults preserve the previous readable slot. A fault after slot rename reports the newly published index and durability error rather than claiming the old bytes survived. Missing, corrupt, unreadable or failed captures cannot become complete successful evidence. Ordinary indexes contain source/profile/run/resource/error and runtime metadata, not full argv, environments or raw process options. Native startup logs retain the existing declared-value treatment and their exact stored bytes.

Recovery and retirement validate receipts without mutation before reserving writer custody, then repeat admission against the fresh registry before claiming its writer. Immutable-version paths require admitted versions inside the registered bundle. A superseded-removal marker cannot authorize committed-index deletion; whole-bundle retirement requires its separate durable inventory. An unrelated listener refusal leaves the previous run's custody inventory unchanged. A registered active writer remains protected without waiting under profile custody. Missing selected-slot evidence after established publication is an actionable error that preserves pending retirement; a genuinely unpublished run may have no slot. Recovery does not reconstruct a missing slot from a bundle.

The committed diagnostic index retains publication authority across later prepared attempts. Its registered ownership and immutable index integrity are validated before requiring the selected slot. Recovery checks that evidence before custody-file mutation and again under acquired custody; missing established evidence preserves the refused registry and pending-file inventory.

Replacement metadata must complete registry publication and directory durability before reclaiming its previous immutable index. Superseded index receipts record removal intent in the same run registry before unlink; recovery reconciles that exact inventory after interrupted removal or inventory publication. Unmarked absence and changed file identity or bytes remain errors. Required cleanup removes superseded versions rather than retaining them indefinitely.

Replacement work becomes pending before atomic temporary registration. Registered temporaries keep recovery eligible independently of a prior attempt's completion flag. Recovery reconciles an interrupted index rename through the temporary's actual registered inode; registered immutable versions remain authoritative, and the selected slot is never a pending-removal target. Required directory durability precedes removal of the pending inventory. Cleanup settles pending files and version retirement before clearing eligibility; the old committed index retains its independent authority throughout preparation.

Returned write, rename and synchronization errors retain pending ownership. Successful atomic publication transfers that responsibility to the caller's registered immutable or committed receipt; the producer does not discard it on error. Initial bundle relocation follows durable index registration, and recovery completes both parent-directory synchronizations before continuing publication.

Profile publication custody follows its registered execution, including one that concludes while its process remains alive. A superseded retry validates the complete selected lineage and retires its own data without republishing an ancestor. Pending-file and owned-tree removal record exact identities before deletion and retain their intent through failed synchronization or metadata publication. Explicit environment export registers its new destination, validates the complete archive and commits completion before removing staging; retries preserve that archive. Native persistence and close errors are retained together.

`exportEnvironmentTo` selects a new absolute archive destination outside automatic cleanup and borrowed resources. At an owned resource's pre-release boundary, the framework stages supported directory files and empty directories with actual hashes and lengths. This includes independent nested scope disposal and allocated acquisition-failure cleanup. Run completion builds the explicit archive from registered staged bytes after resource release. Requested state released without complete staging is an error. Existing targets, foreign symbolic links and unsupported registered state fail explicitly. No database adapter is implemented by this contract; later storage integration must provide actual owned state rather than an empty database export. No environment archive is created by default, and explicit archives are never cleanup roots.

A successful explicit export is terminal during later resource cleanup retries: its archive and completion state remain unchanged, and removed staging is not reopened. Failed, incomplete and invalid export states remain errors.

## Interrupted execution recovery

Standard Node, Jest and Playwright execution setup calls `recoverBeforeRun({ projectRoot, profiles })` for the selected profiles before admitting a run. Configuration loading and test listing allocate nothing. The underlying `recoverRuns` returns explicit `recovered`, `active` and `ignored` run identities. Only `resource-run-v2` registries with complete run/scope/resource identities and real registered boundaries are eligible. PID-only registries, historical scratch, unrelated paths and other worktrees are not adopted. Active execution requires its actual native identity and execution-bound authority. Recovery requires an ended native owner or an affirmative same-native managed execution conclusion, then exclusive registered writer custody and the same writer listener. Unknown local executions, live foreign writers and unrelated listener occupants produce actionable errors without mutation or signaling.

Normal execution and recovery use the same queued registry writer and directory-removal mechanism. Controllers never write registry snapshots. Recovery uses registered provider capabilities; persisted module names and callbacks are not executable recovery inputs. SQL recovery matches current configured credentials to the recorded service and verifies its actual server identity and exact remote namespace receipt before removal. Explicit custom services use runtime `providerOptions.databaseRootUrls`. Failed remote cleanup retains its manifest. Interrupted callback producers retain an interruption report and their original execution identity; recovery never executes the abandoned callback.

Process recovery stops an orphan through its exact execution-bound controller, never by signaling a recorded PID. A live worker without that controller is ambiguous: recovery reports its run/resource identity and retains its data and metadata. Borrowed resources and symlink targets are never deleted. Failed recovery preserves original serialized failures and records its cleanup errors.

The process record registers a staged terminal file and publication-diagnostic file before controller spawn. Its inherited descriptor carries the same-execution outcome after admitted producers, worker closure, authority replies, socket closure, pending sends and IPC closure conclude. Required file/directory durability and descriptor closure precede an exclusive completion link, the final required publication operation. Readable staged bytes without that link retain dependent data. Separate publication diagnostics retain the real failed stage and native cause without authorizing deletion.

Recovered stop consumes the authorized outcome after the exact native controller ends. Preliminary stop replies and native disappearance alone cannot authorize dependent deletion. Missing, partial, mismatched and unknown terminal evidence retains data. Controller failure events bind their identities to complete graph fingerprints. Startup cancellation retains later native originals, and acknowledgement requires that exact content to be retained in the registry transaction. A complete unobserved failure rejects the observing recovery; subsequent recovery can consume its unchanged acknowledged digest while preserving the error prefix. Incomplete publication remains refusal on repeat. A native-confirmed never-started worker remains distinct from a missing worker outcome.

Run errors and registry snapshots use the same original-error collection. Normal stop and recovery retain complete terminal originals before exposing their acknowledgement to queued saves. Trusted event provenance binds the retained Error graph to its event identity and complete cause fingerprint; ordinary caller properties remain payload. A retry requires the unchanged receipt digest and the corresponding event-bound complete graphs in the retained error prefix. Missing event provenance retains data. A final prepare failure preserves the preceding readable registry; a durability failure after rename leaves the newly published registry readable and rejects with its publication stage.

Transport fingerprints identify immutable controller content, not a later diagnostic rendering. Normal acknowledgement and recovery compare the complete retained cause with its validated terminal graph under the same recorded redaction projection. Additional declarations do not change event identity. Missing originals, different events, changed retained content and unavailable redaction policy refuse cleanup and retain data.

Normal finish, recovery and failed admission join authority handlers and socket error producers before terminal error publication. Their exclusive custody receipt remains allocated through final prepare, publication and durability settlement, independently of listener retirement and persisted status. The registered custody directory remains as metadata after its execution receipt is released. Recovery records cleanup failures before intermediate saves and includes previous failures and publication-stage errors in rejection. A prepare failure retains the preceding bytes; a durability failure can follow publication. Local execution conclusions bind the actual run, native identity and execution ID.

Native inspection supports macOS through the boot-session identity and `ps` start timestamp, and Linux through the boot identity and procfs start ticks. macOS timestamps have second precision; equality alone never authorizes signaling or orphan deletion. Controller execution identity supplies process-control authority, and ambiguous identities fail without deletion. Inspection requires the platform's normal native tools/procfs access and private loopback listening. No package dependency, privilege change or runtime-version alternative is installed. Other platforms require a native identity/control implementation before adoption.

The direct CI acceptance entry on a supported platform is `node --test harness/resource-recovery.test.mjs harness/resource-scope.test.mjs` from `tests/`, with Node 24.0.0 and the selected later runtime. Physical listener/process/descriptor observations remain separate from expected native command-failure assertions.
